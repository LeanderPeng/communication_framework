# 学习与实现路线

## 阶段 1：协议帧与编解码

- 定义帧头、版本、消息类型、序号、长度、负载和 CRC16。
- 实现完整帧编码与解码。
- 验证大小端、非法长度和 CRC 错误。

产物：`comm_frame.h`、`comm_codec.c`、`test_comm_codec.c`。

## 阶段 2：RingBuffer

- 实现固定内存环形缓冲区。
- 明确定义空、满、有效长度和溢出策略。
- 验证索引绕回、边界容量和批量读写。

产物：`comm_ringbuffer.h`、`comm_ringbuffer.c`、对应测试。

## 阶段 3：增量协议解析器

- 允许每次输入任意数量的字节。
- 处理半帧、连续多帧、垃圾前缀和损坏帧。
- CRC 错误后能够重新同步到下一帧。

产物：`comm_parser.h`、`comm_parser.c`、字节流测试。

## 阶段 4：有界消息队列与平台适配

- 核心层只依赖抽象接口。
- Linux 端使用 pthread mutex/condition variable。
- RTOS 端映射到目标平台队列与任务 API。
- 定义队列满、等待超时和退出策略。

## 阶段 5：消息管理器

- 统一请求、应答、主动上报和错误消息。
- 使用 sequence 匹配请求与应答。
- 实现 pending、超时、有限重试和旧回复过滤。

## 阶段 6：Appliance Manager 示例

- 把完整通讯消息转换成洗衣机业务事件。
- 更新业务模型，但不直接操作 LVGL。
- 通过 UI 平台适配接口投递刷新请求。

## 阶段 7：工程化验证

- 模拟高频输入、队列满、乱序、重复消息和断线重连。
- 统计收发帧数、CRC 错误、溢出、超时及队列峰值。
- 使用日志和测试复现问题，而不是依赖现场猜测。

当前已完成：Parser、核心帧队列、Linux pthread 帧队列及 Message Manager 的
可选诊断统计。

队列统计使用 `comm_frame_queue_stats_reset(&queue, &stats)` 开始一个周期，
之后统一通过 `comm_frame_queue_push_with_stats` / `comm_frame_queue_pop_with_stats`
记录成功入队数、成功出队数、满队列拒绝次数和历史积压峰值。统计清零不清空
队列，峰值从当前深度开始；普通队列 reset 不算出队，也不清除外部统计。

pthread 队列使用 `comm_frame_queue_pthread_init_with_stats` 启用统计后，普通
push/pop 和 Channel 转发会自动计数；原 init 保持不启用统计。调用方提供的
统计存储必须和队列一起存活，运行期只能通过 `get_stats` 读取独立快照、通过
`reset_stats` 清零，不能直接读写正在使用的统计对象。这两个接口与收发使用
同一把 mutex，关闭后仍可使用，但不能与 init/destroy 并发。

pthread 层分别记录实际入队/出队数、遇满/遇空调用数、进入条件变量等待的
调用数、超时数和历史峰值。同一次调用反复被唤醒不重复计遇满或等待；零等待
失败计超时，但不计等待；等待后成功和关闭唤醒均不计超时。核心 FULL 次数
不能代替这些平台统计，因此 pthread 层自行计数，不对核心统计重复累加。

统计按事件发生时刻归属周期。等待过程中清零会清除先前的等待记录，之后
发生的成功或超时记入新周期，因此清零后的等待数和完成数不一定一一对应。
清零保留已有帧和关闭状态，峰值从当前队列深度开始。

Message Manager 使用 `comm_message_manager_init_with_stats` 启用统计，原 init
保持不启用统计。统计包含通道接受的总帧数、新请求数、通道投递失败数、收到
的请求/上报、匹配 RESPONSE/ERROR、未匹配回复、成功重发、最终超时、pending
满拒绝次数和 pending 峰值。所有累计计数饱和递增，接收与超时事件在回调前计数。

`frames_sent` 包含新请求、重发及非请求帧，只说明通道接受；`requests_sent`
只计新建事务；重发成功增加 `retries_sent`，通道拒绝只增加 `send_failures`。
`request_timeouts` 只计用尽重试次数后结束的事务，不计队列投递超时、manager
复位或中途清统计。重复/迟到回复归入 `unmatched_replies`，不重复计匹配成功。

`comm_message_manager_get_stats` 复制快照，`comm_message_manager_reset_stats`
清零累计值并从当前活动请求数重设峰值，不改变 pending、序号或截止时间。
manager 普通 reset 保留历史统计。已有事务在清零后产生的回复、重试和超时
归入新统计周期，所以新周期的完成数不一定等于新周期发出的请求数。

统计接口与 manager 一样不加锁，必须由所属任务串行调用，不能在事件回调中
重入。其他任务需要读取时，由所属任务取得独立快照再经队列交接；pthread
队列统计的加锁读取方式不能直接套用到 Message Manager。

### 字节流级集成测试（已完成）

`tests/test_appliance_stream_integration.c` 串联以下链路：

```text
状态查询 -> Message Manager -> TX Channel / pthread 队列 -> Codec 编码
    -> 模拟对端解码请求、读取序号并编码回复
    -> 分段字节 -> RingBuffer -> Parser -> RX Channel / pthread 队列
    -> Message Manager 匹配请求 -> Appliance Manager 更新模型 -> 通知回调
```

模拟对端从请求字节中读取序号，接收帧必须经过 RX 队列才交给消息管理器。
测试覆盖：

- 响应全部 18 个两段拆分位置、逐字节输入和环形缓冲跨尾部写入。
- 多帧粘包、两个请求乱序应答、重复应答、主动上报及相同模型去重通知。
- 垃圾前缀、伪同步字、CRC 错帧、超长长度候选后的重新同步。
- 重发字节与原请求一致、重试后成功、最终超时后的迟到回复过滤。
- CRC 合法但业务字段非法时拒绝更新模型，之后正常查询仍可成功。
- RX 消费前不能更新 pending 或模型；原始字节和解析临时缓冲改写后，
  队列中的帧副本仍然有效。

当前行为边界：sequence 用于匹配事务，不表示业务快照的新旧。两个不同请求
的合法回复按接收顺序更新模型；重复回复因事务已结束而被过滤。匹配成功后
pending 即结束，即使业务层拒绝非法字段，也不会自动触发该请求的超时重试。

这一步使用真实 pthread 队列和确定性模拟时间，所有阶段在一个线程内执行。
尚未验证真实传输、任务调度、持续流量下的背压、断线重连或电源板协议。

### Linux 多任务运行示例（已完成）

`examples/linux_runtime/main.c` 使用主线程串行管理请求及业务模型，另外启动
发送、接收和模拟设备三个 pthread 线程。模拟设备通过本地流式 socket 收到
查询并返回响应，不直接访问本端状态。编译及运行说明见
[Linux 运行示例](../examples/linux_runtime/README.md)。

- 接入 `CLOCK_MONOTONIC`，每轮最多处理一帧再检查超时，避免持续输入饿死重试。
- 收发处理短读、短写及 `EINTR`，按 RingBuffer 剩余空间读取，保留半帧。
- TX 满时零等待返回；重发投递失败保留到期事务，下一轮再次尝试。
- RX 满时保留当前完整帧、暂停读取并等待空位，让流式 socket 的背压向对端传播。
- 提供正常查询、丢首次回复、持续不回复、队列积压恢复、积压时停止、断连和
  空闲停止场景；支持 Ctrl+C / SIGTERM。
- 统一停止入口先关闭队列、shutdown socket，再 join 线程，最后释放资源。
  初始化或线程创建中途失败也回收已经取得的资源。停止允许放弃未完成事务。

验证覆盖七种运行场景、信号退出、线程创建三个位置的失败、socket 创建失败、
短读短写及 EINTR 注入、阻塞发送时停止、重复初始化/运行/回收和 TX 满拒绝。
原有 13 个测试程序通过；运行场景及生命周期验证通过 ASan / UBSan / TSan 检查。
临时故障注入与生命周期验证程序不属于产品代码，不加入提交。
